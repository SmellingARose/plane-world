Aero table accuracy

You pick one accuracy, such as ±5 %. Half of it goes to table spacing: points are added only where interpolation misses by more than that, mostly near stall. The other half goes to the CFD grid, sized from a measured grid-convergence error. Each pack stores its error map, so FLY can show how accurate the aerodynamics are at any moment.

The process

Steps 2 and 3 are the decisions; everything else is automatic. Each has several workable options, compared below.

CFD methods in plain words

The core problem. Air flowing over a wing breaks into swirls (turbulence) of every size, from swirls as big as the wing down to ones smaller than a grain of sand. The tiny ones matter most right against the plane's skin: that thin layer is where friction drag comes from, and where the flow peels off the wing when it stalls.

Every CFD method chops the air into small cells and calculates what happens in each one. Swirls smaller than a cell can't be seen, so they have to be estimated with a formula. The methods differ in how small the cells are, which decides how much they calculate and how much they estimate.

Body-fitted grid (SU2)

Cells are shaped to wrap snugly around the plane, like a wetsuit, so the thin skin layer is captured well. Making the wetsuit is the hard part: it can fail on odd shapes and has to be redone when a flap moves.

Cartesian grid (our GPU solver)

Plain cubes, like Minecraft, with the plane dropped in. It never fails and parts can move freely, but the cubes are blocky at the skin, so that layer is estimated. That caps accuracy around ±3–5 %.

How the grid is built is a separate choice from which method runs on it: RANS can run on either grid, for example.

The ideal way, for precision engineering

No single solver is "the answer". Industry databases (airliners, NASA's SLS) are built as a stack: body-fitted RANS for the attached-flow envelope, scale-resolving simulation where flow separates, and wind-tunnel and flight data to validate it, with every number carrying a measured uncertainty. So why not always SU2?
  • Cost. A body-fitted RANS case runs on the CPU for roughly an hour, versus minutes on your GPU; a 500–1,000 case pack becomes weeks.
  • Meshing. Plane World crafts are overlapping primitive parts. Body-fitted meshing needs them merged into one watertight surface first, and it can fail on thin or touching parts. The immersed-boundary grid never fails.
  • Moving parts. Each control deflection needs a deformed or new mesh; the Cartesian grid just re-stamps the part.
  • It still isn't "ideal" at stall. RANS, in SU2 or anywhere, gets separated flow wrong; that needs DDES or LES on top.
If precision is the goal
  • Body-fitted, grid-converged RANS (k-ω SST) for the attached envelope, with a grid-convergence error on every point.
  • DDES at the separated points: stall, post-stall, rocket base flow.
  • Our GPU solver only for drafts and to plan where the expensive cases go.
  • Any wind-tunnel or flight data you have, to validate and correct the pack.
  • Accept the cost: a precision pack is days to weeks of compute, not a night.

What SU2 is

SU2 is a free, open-source CFD program started in 2012 at Stanford's Aerospace Design Lab and now developed by an international community. It solves compressible and incompressible RANS with standard turbulence models (Spalart–Allmaras, k-ω SST) on body-fitted meshes, whose cells follow the craft's surface. That lets it resolve the thin boundary layer properly, which is where our solver is weakest. It also does mesh deformation and adjoint shape optimisation.

How it would fit: Plane World writes the craft surface and a settings file, an external mesher (e.g. Gmsh) builds the mesh, SU2 runs on the CPU (MPI, all 28 threads), and we read its force files back. Licence is LGPL 2.1, and since we only run it as a separate program it does not affect Plane World's licence. Native builds target Linux and macOS; on your Windows PC it would most likely run under WSL2 (to be confirmed).

Questions for you

  1. Precision or speed first?
    precision stack (body-fitted RANS + DDES at stall, days–weeks per pack) · fast GPU packs first, precision stack added later · GPU only
  2. Cases: base table + increments, adaptive sampling, URANS with warm starts as the defaults?
    yes · something else (say which row to change)
  3. What should "±5 %" mean?
    percent of each coefficient's full range (recommended) · percent of the local value · absolute, e.g. ΔC_L ≤ 0.02
  4. Which craft first?
    Trainer (recommended) · Racer quad · New Shepard (needs SU2 above Mach 0.3)
  5. How far should the envelope reach?
    normal flight (α −10…+25°) · post-stall to ±90° (hover, VTOL, landing rockets) · all directions
  6. Which toggles in version one?
    props · engine plume · control surfaces · ground effect · rotation damping (each ≈ +15–30 % cases)
  7. After a BUILD edit makes a pack stale?
    fast model with a warning · keep old pack, marked stale · regenerate in the background
